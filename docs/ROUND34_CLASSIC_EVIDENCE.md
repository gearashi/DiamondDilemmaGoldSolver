# Round 34 classic GPU exhaustion evidence

The classic CUDA and WebGPU runners now archive the transitive solver sources for both engines. The integrated classic capture covers 166 source files. An exhaustion record binds the input, frontier file, objective, GPU reasoning policy, complete source set, origin run, completed jobs and candidate count. On restore, the runner checks the source bytes in that original archive, the current implementation and the validated job ledger. It accepts equivalent LF and CRLF source layouts.

The checkpoint writer hashes the actual uncompressed NPZ bytes as NumPy writes them. It publishes the per-generation receipt in the originating run's archive before atomically replacing the native checkpoint. The terminal JSON is published after the native save succeeds. A valid terminal checkpoint reconstructs a missing terminal JSON. A previous partial checkpoint alongside a later terminal JSON resumes its outstanding branches. A mismatch in a current terminal's checkpoint receipt, source files or result leaves the checkpoint and original result available for investigation. A changed implementation or lost source while resuming an active checkpoint preserves the search position and independent verification of any Gold board. If those branches finish without a board, the dashboard reports **Saved branches finished with unverified coverage**.

## Released v1.14.0 migration

The old writer recorded raw source hashes, a hash of the exact frontier NPZ, the puzzle, policy, final totals and counters, checkpoint size and generation. It omitted a collision-resistant digest of the native checkpoint. Each reviewed original CUDA and WebGPU source set is pinned by one digest of its filename-to-normalized-content-hash map, covering 131 and 134 source files respectively. The runner checks the actual archived bytes against the recorded raw hashes and reconstructs the partition with the current deterministic planner. It accepts a completed fresh historical run with its matching original exhaustion record, archived config and final status and completed job ledger. The migration writes a new native checkpoint and matching receipt. Reopening it again uses that receipt.

For a nonempty historical partial, byte length and counters alone cannot distinguish an edited but valid stack. For a fixed-budget chain in the supported GPU-only profiles, the runner can independently replay the original sequence without the newer physical-mate filter, including lane resizing, and compare every native field and job-ledger array. This recovery is limited to 1,024 simultaneous old lanes, 8,192 dispatches and two million lane work units to bound startup memory and work. An untouched generation-zero checkpoint can instead establish that no earlier GPU steps were pruned and recheck the whole stored frontier. An incomplete history, unverifiable branch exclusions or replay outside the bounded recovery path can still resume for finding a Gold board. The older CPU-assisted and adaptive partials generally lack the data required to reproduce their scheduling exactly. An empty saved partition can be independently replanned without launching the GPU.

## Controls

On an RTX 2060, a genuine published v1.14.0 CUDA runner on a 160-piece closed-loop fixture stopped at generation 4,934 after 19,652 candidate tries. The one-time verification independently repeated those 19,652 tries to compare native state. The resumed search completed all 480 jobs at the cumulative search counter of 230,400. Reopening the completed result at a different lane count added zero tries. A separate fresh v1.14.0 terminal migration and its second reopen also kept 230,400 unchanged. Altering one RNG word in a valid historical partial while retaining the NPZ byte count and every reported counter correctly yielded unverified coverage. An untouched old generation-zero partial with no matching original final status was verified by comparison with the replanned 480-job partition. Removing one job and recomputing the frontier and checkpoint's stored hashes was rejected.

The runner tests include a rehashed result missing the physical Gold module, lost sidecars, an altered archived source, progress preserved after receipt loss, recovered output ordering, dashboard state and an independently validated Gold board recovered from an unbound historical partial. The deterministic host fixture's 480 jobs took 1,440 work units, checked for duplicates across interruption and resizing. It tests runner behavior independently of the GPU search algorithm.

## 62. Verify a saved exhaustion without a GPU

A current terminal native checkpoint and archived receipt let the runner check the file SHA, puzzle, objective, policy, source files and completed ownership on the host. The runner reads the counters, job IDs, depths and terminal flags from the archive. It requires zero open jobs and zero pending lanes. It does not upload the board stacks or allocate a replica pool. On the genuine RTX 2060 migration control the second reopen at 128 requested replicas used **zero GPU allocations and zero search launches**, with all 480 jobs and 230,400 candidate tries retained. Positive Gold witnesses still pass the independent CPU board validator.

The dashboard exposes **Verify saved exhaustion** when the selected classic reasoning profile has a matching saved terminal and its GPU backend is unavailable. The server checks the header again and launches a verification-only child. That child rechecks the original evidence and cannot start a new GPU search. Three consecutive status polls on an unchanged checkpoint opened its header once. New files and atomic replacements change the cache identity. With the GPU unavailable and Hall enabled, the Node DOM test selected the saved profile, clicked Verify, and inspected the submitted verification-only request. Different profiles and active jobs retained their normal controls.
